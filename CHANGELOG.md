# Changelog

All notable changes to dark-factory are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- Project profile schema `profile/schema.json` (JSON Schema 2020-12, unknown fields rejected) and `loadProfile(projectRoot)` in `profile/load.js`, the single reader of `.factory/profile.json`; errors name the offending field by full path. Ralph is off by default (`ralph.enabled`); the schema has no way to exclude base skills. Adds the `ajv` dependency and the `profile/` package directory.
- Fixture profiles "monorepo" and "single package" (`test/fixtures/profiles/`) for core tests, and example profiles of the consumer projects with their current values (`examples/profiles/`); `npm test` now includes `examples/**/*.test.js`. Neither directory ships in the package.
- Acceptance Verifier core in the new package directory `verifier/`, moved from the consumer project's verifier at its reference commit with the same verdicts on the same inputs: the verdict CLI `verifier/verdict.js` and its modules `verifier/verdict/`, the model prompt `verifier/prompt.md` and output schema `verifier/schema.json`, the input producers (`affects-scope.js`, `test-tampering-scan.js`, `spec-hash.js`, `label-authority.js`, `issue-lint.js`, `factory-separation.js`, `metrics.js`) and the golden eval engine `verifier/eval/`. Project literals were removed from the code, prompt and test fixtures.
- Deterministic verifier checks are modules in `verifier/checks/` with one interface (context in, FAIL reasons out) and are called only through a registry: `spec-approval`, `affects-scope`, `computed-items`, `test-tampering-scan`, `references`, `ci-checks`, `allowed-model`. A check declares its reason codes at registration; the closed list of codes is the core's plus the declared ones. Profile knob `verifier.checks` picks the checks that run; **none run by default**. A name no registered check has fails the verdict (`unknown_check`).
- Risk zones (`verifier/risk-zones.js`): the core's base list (`auth`, `secrets`, `ci`, `fs_shell_sinks`, `dependencies`, `none`) plus the project's zones from its trusted `.github/verifier/risk-zones.json`, rendered into the prompt (`{{RISK_ZONES}}`) and the schema enum. A project can only add zones; removing or redefining a base zone is rejected. The verdict CLI takes `--project <root>` (profile) and `--risk-zones <file>`; an invalid profile or a missing or invalid zone config fails the verdict (`config_invalid`), and a report naming a zone outside the merged list fails it.
- The golden eval engine reads its case directory from the profile (`verifier.goldenDir`, via `loadProfile`): `verifier/eval/verifier-eval.js --project <root> <results-dir>`; without the field it exits with an error naming it. The case format is unchanged.
- Reusable workflows (`workflow_call`) that projects call from short wrappers, moved from the consumer project's own workflows: `.github/workflows/acceptance-verifier.yml` (jobs `Verify`, `Verify second`, `Report`, status `Acceptance Verifier`), `acceptance-verifier-eval.yml` (golden eval), `spec-approval.yml` (spec freeze on `spec-approved`) and `factory-separation.yml` (check `Factory separation`). Verifier code comes only from this repository at the SHA the wrapper calls (`factory-sha` input); the profile and trusted configs (`.factory/profile.json`, `.github/verifier/`, including `risk-zones.json`) only from the project's default branch; the PR head is data only. The branch template and golden case directory come from the profile, the model and enforce mode from wrapper inputs (project variables `VERIFIER_MODEL`, `VERIFIER_ENFORCE`; advisory by default), `OPENAI_API_KEY` from an explicit `secrets:` entry. Example wrappers in `examples/wrappers/`. Nothing runs until a project adds a wrapper.
- `verifier/factory-version.js`: reads the factory release tag from the `dark-factory` dependency in the project's default-branch `package.json`. It checks that the dependency installs from this repository and that the tag resolves to the wrapper's SHA (`factory-version.js verify`). The workflow fails, and the verifier verdict is `FAIL`, on any of these: a floating reference (branch, `latest`, range, no tag), a missing dependency, another repository, a tag that does not exist, or a tag on another commit.
- `profile/branch.js`: the issue number of a task branch from the profile's `branchTemplate` (`{issue}`, `{slug}`, all other text literal). The reusable verifier uses it in place of a hard-wired branch prefix; a branch the template does not match is not verified.
- `npm test` checks the package content (tracked files under the `files` directories, `package.json`, `README.md`) for project literals via `.claude/scripts/core-literals.js`; a finding fails the existing `Test (Linux)` and `Test (Windows)` jobs with file, line and literal. Development-only; nothing ships.
- Issue contract in the core: `verifier/issue-contract.json` and `.md` (moved from the consumer project) plus the project overlay `.github/verifier/issue-contract.overlay.json`, read from the default branch; a missing file is an empty overlay. The overlay can only add sections and forbidden phrases; removing or weakening a base section or phrase, or an unknown field, makes the issue invalid with the reason named. A section has alternative names (`Контекст` is also `Context`); the linter, the Affects scope finder and the workflow find sections by name or by `role` through the contract, with no name lists of their own. Section and `Affects` headings are now matched exactly (case-sensitive), as the linter always did; the early acceptance-section check no longer accepts other heading levels or spellings the linter would reject anyway. `issue-lint.js` takes `--overlay` (replaces `--contract`) and `--has-role`; the verifier workflow replaces its grep for the acceptance section with it. No profile knob; this is part of the issue contract and applies to every verifier run.
- Integration tests of the verifier on both fixture profiles (`verifier/profiles.test.js`, fixtures in `test/fixtures/verifier/`): the verdict from a fixed model report and other fixture inputs, `out_of_scope_file` on temporary profile copies with `affects-scope` enabled, a dummy check that is wired in only by registration and a profile entry (enabled: adds its reason; not enabled: verdict unchanged), and the golden eval on a PASS and a FAIL case per profile with results computed by the real verifier code. The fixture profiles gained `verifier.goldenDir`; their sets of enabled checks are unchanged. Tests only: no core code changed, no knob, nothing ships.

- Calibration Judge, an **optional** element, moved from the consumer project into the new package directory `judge/` (its tests in `judge/**/*.test.js`; `judge/` is in `files`, in `npm test` and in `tsc --noEmit`). Judge analyses a failed or undecided Acceptance Verifier round, attributes the cause to the issue, the implementation, the verifier or the infrastructure, and only observes: it never changes a verdict, the `Acceptance Verifier` status or a label, and is never a required check. Its prompts, response schemas and inputs config (`judge/inputs.json`) are in the core, without references to a project. **Off by default**: profile knob `judge.enabled` (default `false`; an absent section is the same) and `labels.calibration`, required only when `judge.enabled` is `true` (a root `allOf` condition, checked by `loadProfile`, which names `labels.calibration` when it is missing). Without `judge.enabled: true` every start, a manual one included, is an ordinary skip with no model call and no comment; an invalid or missing profile, or a wrapper SHA that is not the project's pinned release, is a configuration error (logged and in the summary; an automatic run ends without error, a manual run fails). Reusable workflow `.github/workflows/calibration-judge.yml` (`workflow_call`; inputs `factory-sha`, `judge-model`, `verifier-model`, `pr`, `run-id`, `run-attempt`; explicit secret `OPENAI_API_KEY`) and the example wrapper `examples/wrappers/calibration-judge.yml` keep the four ways to start it: a finished verifier round, the calibration label added to the PR or its issue, and a manual run. The branch template comes from the profile (`profile/branch.js` in every lookup: PR check, issue number, PR of a labeled issue, input collection), the label from `labels.calibration`, the owners from `.github/verifier/owners.json`, the taxonomy and allowed models from the project's `.github/calibration/`, the Judge model from the wrapper input. Judge code comes only from the factory checkout at the wrapper SHA, project settings only from the default branch, the PR head is data only, the key reaches only the two model steps. Expected failures of an automatic run (inputs and artifacts of the round, model steps, a rejected model) are absorbed in the job where they happen and reported as an analysis error. Judge uses `verifier/label-authority.js` and `verifier/verdict/common.js` instead of copies. The status context and the wrapper path of the verifier are shared constants in `verifier/round-protocol.js`. New profile example values: `examples/profiles/jobflow` enables Judge with its current label.
- Policy snapshot of every verifier round: new `verifier/policy-snapshot.js` and, in the `Verify` job of `acceptance-verifier.yml`, the steps `Form policy snapshot` and `Upload policy snapshot` (artifact `policy-snapshot`, which `Report` does not download). It records the rules the round used: the profile and its enabled checks, risk zones, owners, required checks, the verifier's allowed models, the tampering config, the prompt and schema the model was given and the issue contract with the project overlay, each with a hash and a state (`saved`, `absent` in the trusted checkout, `unused` by the round, `unavailable`, with the reason), plus a format version and the origin (factory SHA, SHA of the trusted settings checkout, head commit, run ID and attempt). It has no switch, because it adds no check, no model call and no authority and does not touch the verdict: a failure to form, write or upload it only logs a warning and a summary line and cannot fail the job; the verdict is computed from the same inputs as before. Judge reads the snapshot of the current and of the previous round as data and, when a round has none, an expired or an untrustworthy one, marks that historical input as incomplete instead of using the current settings.
- Profile schema extension (all fields optional; a profile valid before stays valid, nothing is added when they are absent): `ralph.humanNeededVerdict` (name of the "human needed" verdict; a token without whitespace or colon that is not DONE, BLOCKED, TYPE, SUMMARY, REVIEW or CODEREVIEW), root `install` (project-level installation steps in the shared `argv`/`cwd` command format, run before `apps[].install`), the `{file}` token in `hooks.lint[]`/`hooks.typecheck[]` `command.argv` (absolute path of the changed file; a literal in install and gate) with the documented hook selection order and glob dialect (minimatch), and compound `skillRules[].extensions` (`.test.ts`, `.d.ts`). Malformed extensions (no leading dot, empty or trailing segment, whitespace, path separator) are rejected. Schema, loader tests and example profiles only; execution is in later tasks. The example profiles of `jobflow` and `cards` now record their blocking verdict, the root install, the lint/typecheck hooks and the narrowed vitest rule.

- Ralph Docker sandbox runtime in the new package directory `ralph/` (in `files`, `npm test` and `tsc --noEmit`), moved from the consumer project: `ralph/sandbox.js`, `ralph/sandbox/Dockerfile`, `ralph/sandbox/proxy.js`, with its contract in `ralph/sandbox/README.md`. The runtime uses Node built-ins only and starts nothing on require (the proxy listens only when run as the entrypoint); it keeps the home-directory, mount, work-directory, capability, secret-in-argv, proxy-allowlist and cleanup protections, and has no host fallback. New profile section `sandbox` (`image` with an explicit `name:tag`, `nodeVersion`, exact `claudeCodeVersion`, `allowedHosts`, optional `installEnv`; unknown fields rejected), **required when `ralph.enabled` is `true`** and validated in full whenever given; Ralph stays off by default. `loadProfile` validates it with the same `validateSandboxConfig` rules the runtime uses and names the file and the full field path. The runs root is not a profile setting: it is the optional `runsRoot` of the consumer's local run config outside Git (default `<consumerRoot>/.ralph-runs`; a path inside the home directory is rejected). Portable tests run without Docker, network or AI; the original Docker scenarios are kept as a reference snapshot with a map in `test/fixtures/ralph-sandbox/` and are **not** claimed as passed until the Docker integration task. Call arguments are validated before any Docker or filesystem action (`image` with an explicit tag, `rootKey`, `runLabel`, `network`, `name`, the `startProxy` inputs including every allowed host, and `removeLeftovers`'s `rootKey`), and a variable name set from two sources (`env` with `publicEnv` or with the added proxy variables) is rejected by name. The proxy limits destinations by name only; this is documented. The example profiles of both projects and the fixture profiles gained a `sandbox` section.

- Base set of the package, moved from the consumer project's copies (the commit named in the task): process skills `prd`, `plan`, `issues`, `task-lifecycle`, `epic-discovery`, `adr` and `modern-javascript` (with its references) in `skills/`, agents `research`, `codebase-scan`, `verify`, `pr-writer` in `agents/`, and `skills/base-set.json`, which lists them with their sources. The other JS metaskills (`js-conventions`, `js-gof`, `js-data-structures`, `error-handling`, `data-structures`) come from the npm package `metaskills`, now a pinned runtime dependency (`1.0.5`) instead of a dev dependency. The installable set of six JS metaskills and the five that the path table **requires** (`requiredJsSkills`) are separate lists. `code-review`, which the Ralph code-review pass calls, is recorded in `runtimeSkills` as a skill bundled with the pinned Claude CLI (version: `sandbox.claudeCodeVersion` of the profile), not a plugin and not shipped here; that the pinned CLI really bundles it is for the Docker integration task, not for `npm test`. Project literals, project paths and ADR numbers were removed from the moved texts. `issues` and `task-lifecycle` use the linter and contract of the installed factory (`node node_modules/dark-factory/verifier/issue-lint.js <file> --require-v2`, `node_modules/dark-factory/verifier/issue-contract.md`); `adr` takes its file from `docs.adr` and says that none is configured instead of assuming a path. Texts stay in Russian where they were until the translation task; full overlay and parameterization checks are a later task.
- **Deliberate behavior change of the moved `verify` agent (narrower than the original):** it runs only the `apps[].gate` commands of the apps whose `apps[].path` covers a changed file, in order, each `argv` element as one argument without shell expansion, `{file}` literal, no install, no default commands. The original's conditional logic (build "if it can affect it", end-to-end tests "if endpoints are touched", the tooling-JS section) is not carried over; a build can be an ordinary `gate` command. Checks that need live infrastructure stay separate project checks (CI or a human); adding such a command to `gate` does not lift the `network: none` limit of the Ralph gate. The report states PASS/FAIL per command, NOT RUN (app without gate), NOT COVERED (files outside every app path) and "No checks were run", and never presents a passing gate as all project checks passing.
- Shared "path → skills" table in `profile/skill-rules.js`: `requiredSkillsFor(profile, textOrPaths)` is the one algorithm for Ralph and the hooks (a string is an issue body and only its Affects section counts; an array is explicit paths). Base entries: JS/TS files (`.js .mjs .cjs .ts .tsx .jsx`) anywhere require the five base metaskills; the `docs.adr` file (exact match after separator normalization) requires `adr`. Profile `skillRules` only add. Matching is by whole path segment, `.` covers the project, separators are normalized, compound extensions are file name suffixes, a mentioned directory includes its possible extensions conservatively (it never adds `adr`), results are unique. Profile schema: `docs.adr` is now described as the path of one file, not a directory. The rule is stricter for projects that required fewer skills before (for example `.ts` now requires five skills). The example profiles drop `skillRules` entries that only repeated a base skill, and the jobflow example sets `docs.adr`.

- Ralph controller moved into the package (`ralph/`: `run.js`, `core.js`, `github.js`, `workspace.js`, `prompts.js`, `parsing.js`, `agent.js`, `boundary.js`, `config.js`, `README.md`), wired to the sandbox runtime and the shared path-to-skills table. **Off by default** (`ralph.enabled`) and **not yet ready to run from an installed package** (step registry, profile lookup from the git root, skills setup in the clone, hooks, Docker integration and the packed-package check are later stages; `ralph/README.md` lists them). The controller works in the consumer repository named by an explicit `--consumer-root` with its validated profile and a personal local run config outside Git (`<consumerRoot>/.ralph/config.json` by default; `branchPrefix` is rejected in favour of `branchTemplate`); every git/gh call gets an explicit cwd. Before the lock, the clone and the agent it checks the settings an enabled controller needs (`ralph.humanNeededVerdict`, `labels.humanNeeded`, `ralph.techDebtTrackerIssue`, `sandbox`), the runs root (lock, state, clones and logs live there), the consumer repository and its origin, and that the labels `ralph-blocked` (core constant) and `labels.humanNeeded` exist; it never creates labels. Project values come only from the profile: protected paths (plus the core `.git/` and `.claude/`), doc-only patterns, install/gate commands, rule files, environment limits, the human-needed verdict (matched literally) and the tech-debt tracker. The agent's check commands are derived from `apps[].gate` (exact argv and argv + ` *`); git is read-only (`status`, `diff`, `log`; review passes also `show`), no gh. Agent, installs, dependency sync and gate always run in the sandbox (read-only `.git`; run network with the proxy for agent and installs, no network for the gate; `installEnv` only for installs and sync). Deliberate behaviour changes from the reference: a failing root or app install is BLOCKED (no best effort); a missing required skill is BLOCKED before the agent; branches start from the consumer's default branch read from the clone (no `main` literal); existing PRs and leftover branches are found by `issueNumberOfBranch`, so a title change does not create a second branch; every BLOCKED outcome sets `ralph-blocked`, the human-needed verdict also `labels.humanNeeded`; review-fix summaries are listed in the issue comment while the commit and PR keep the implementation's TYPE/SUMMARY. `CLAUDE.md` invariant 4 now states the agent's read-only git access.
- Profile: optional `dependencySync` at the root and in `apps[]` (arrays of the shared command format): after the agent changed the root `package.json` or exactly `<app.path>/package.json`, the controller runs the commands of every affected area once in the sandbox before the final gate; a manifest without a serving command, a manifest outside the root and app paths, or a failing command is BLOCKED. The commands must not run lifecycle scripts (npm: `npm install --ignore-scripts`). The descriptions of `protectedPaths` and `docOnlyPathPatterns` now fix their glob semantics.
- `profile/path-patterns.js`: the one matcher of the profile's path patterns (minimatch: `*`, `**`, `{a,b}`; `X/` is all of `X`; protected paths case-insensitive and covering `X` itself; doc-only case-sensitive; never a string prefix). `minimatch` is now a direct runtime dependency.
- `profile/branch.js`: `branchNameFor(template, issue, title)` and `slugify`; a template that does not recognize its own branch name is a configuration error.
- Example profiles: `dependencySync` with `npm install --ignore-scripts` (root and both apps of `jobflow`, the root app of `cards`) and doc-only globs `**/*.md`, `**/docs/` (and `**/project-management/` for `jobflow`); protected paths unchanged.
- Portable controller tests (`ralph/*.test.js`) on both fixture profiles without network, Docker or a model. The reference Docker scenarios of the controller suites are recorded in `test/fixtures/ralph-controller/` and are **not** verified until the Docker integration task.

- Ralph step pipeline: the controller's passes are steps in a registry (`ralph/steps/registry.js`; base steps `implement`, `self-review`, `code-review`, `final-gate` in `ralph/steps/`, moved out of `ralph/core.js` — they are the existing pipeline, not new extensions). A step is data: kind `agent` (mode `read-only` or `writes`, a named controller permission profile `implementer`/`reviewer`/`code-reviewer`, prompt builder, output parser, and for a read-only step an optional fix with its own budget) or kind `check` (deterministic code, no model; `final-gate`). `ralph/core.js` runs the resolved pipeline and keeps every protection for every agent call, fixes included: the named permission file, sandbox and environment, timeouts, the task's time and cost budget, the boundary check after each call, the unchanged-tree check after each read-only call (against the state right before that call), a non-empty diff and DEL_RALPH after each write call. Dependency sync runs right before `final-gate`; a doc-only diff skips the reviews and the gate commands and records `final-gate` as `skipped`. The result of `runIssue` gains `steps` (`{ name, outcome }` in order; on a stop the failing step is last); statuses, BLOCKED reasons, labels and the commit/PR/comment content are unchanged. `runRalph` takes a prepared registry as `deps.stepRegistry` (default registry otherwise); no code is loaded from the profile. `ralph/workspace.js` exposes the named permission profiles (`writePermissionProfile`).
- **Changed meaning of `ralph.enabledSteps`:** it is no longer "optional steps switched on, required and possibly empty" but the complete pipeline. Absent (now allowed with Ralph enabled) means the baseline `implement`, `self-review`, `code-review`, `final-gate`; an explicit list is the whole pipeline with `implement` first and `final-gate` last (each once), `self-review` before `code-review` when both are listed, other registered steps in between; `[]` is invalid. `loadProfile` checks the structure; `prepareRun` checks the names, the budget keys and the steps' permission profiles against the registry in force before the lock, the clone and the agent, even with an empty queue. New optional `ralph.stepBudgets` (step name -> integer >= 1, number of fix calls; defaults `self-review` 2, `code-review` 2; budgets are independent; a key that is not a registered step with a fix is a configuration error). The constants `MAX_REVIEW_FIX_ATTEMPTS`/`MAX_CODE_REVIEW_FIX_ATTEMPTS` are removed from `ralph/config.js`. The structure is checked whenever the field is present, also with Ralph disabled, so a profile that still has `"enabledSteps": []` must drop it before moving its pin to this release; profiles drop `enabledSteps: []`; the `cards` example sets `stepBudgets` 4/2, the `jobflow` example keeps the defaults 2/2.

- Ralph finds its project and keeps its settings trusted: `--consumer-root` is now optional (an explicit path still wins and must be the top of a git repository; a wrong one is an error, with no fallback); without it the CLI uses the git top-level of the current directory, so a run from a subdirectory works, and outside git it stops with an error about the root before the lock and the clone. The host profile (missing: error with the expected path; invalid: error with the field) is loaded before the lock. `runRalph` takes a deep, recursively frozen copy of the profile as the one snapshot of the run (the caller's object stays mutable); after each issue's checkout of the selected base, including a dependency's branch, and before the proxy, installs and the agent, the clone's profile is loaded with `loadProfile` and compared with the snapshot by JSON value (key order ignored, array order kept); a missing, invalid or different one stops the issue's preparation with an error naming host, clone and base, with no automatic repair. `.factory/profile.json` is now a mandatory core protected path: a change or deletion by the agent is BLOCKED with no further step, commit, push or PR. No profile schema field and no pipeline change.

## [0.1.0] - 2026-10-12

### Added

- Package skeleton: `files` layout, `private: true`, `engines.node` `>=22`.
- Tag-based releases: the `Release` workflow checks that the `vX.Y.Z` tag matches `package.json` `version` and that `CHANGELOG.md` has a `## [X.Y.Z]` section before creating a GitHub Release.
- CI job `Test (Windows)`.
