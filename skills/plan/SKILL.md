# Plan Generator

Прочитай PRD: `$ARGUMENTS` — если это путь к файлу, читай напрямую; если это kebab-case имя
фичи, ищи `PRD-$ARGUMENTS.md` в каталоге `docs.prd` из `.factory/profile.json`. Если поля `docs.prd` нет, а путь не дан — спроси пользователя.

Если PRD-файл не найден — сообщи об этом и останови выполнение, не выдумывай содержимое PRD.

Создай план реализации и сохрани в файле `PLAN-<kebab-name>.md` (то же kebab-case имя фичи, что и
у PRD-файла) в каталоге `docs.plans` из `.factory/profile.json`. Если поля `docs.plans` нет — не
выбирай каталог сам, спроси пользователя. Если каталога нет — создай его.

Этот план — черновая раскладка PRD на фазы, а не сами GitHub issues. Следующий шаг после плана —
скилл `issues`, который заводит каждую фазу как milestone, а каждую задачу — как issue (источник
правды). Старт реализации любой фазы всё равно идёт через обычный Plan-first / Issue-first /
Branch-first protocol из скилла `task-lifecycle` — этот скилл их не подменяет и не ускоряет.

## Структура плана

Получи шаблон из установленного пакета фабрики — это единственный источник структуры и
содержательных инструкций секций, своей копии шаблона не держи. `<root>` — явный абсолютный
корень проекта (корень репозитория), путь в кавычках, если в нём есть пробелы; команда не зависит
от текущего каталога:

```sh
node "<root>/node_modules/dark-factory/skills/templates.js" plan --project "<root>"
```

Выведенный Markdown — основа документа плюс дополнительные секции проекта (из overlay профиля), они
идут после основы. Используй выданный шаблон целиком и в его порядке. Если команда завершилась
ошибкой (код не ноль, причина в stderr) — остановись и сообщи причину пользователю; не подставляй
шаблон по памяти.

Ветка эпика. Имя base-ветки не собирай вручную: оно строится существующим `branchNameFor` из
`profile/branch.js` пакета — `branchNameFor(profile.branchTemplate, <номер трекера>, "<короткое имя
эпика>-base")`:

```sh
node -e "const [root, issue, name] = process.argv.slice(1); const p = root + '/node_modules/dark-factory/'; const { loadProfile } = require(p + 'profile/load'); const { branchNameFor } = require(p + 'profile/branch'); console.log(branchNameFor(loadProfile(root).branchTemplate, Number(issue), name + '-base'))" "<root>" <номер трекера> "<короткое имя эпика>"
```

Номер трекера известен только после заведения трекинг-issue; пока его нет — назови правило
(`branchTemplate`, номер трекера, короткое имя эпика с суффиксом `-base`), а не придумывай номер.

## Правила разбивки на фазы

- Каждая фаза должна давать рабочий результат.
- Фазы независимы, можно остановиться после любой.
- Первая фаза — как минимальный рабочий путь (Tracer Bullet).
- Не больше пяти задач в одной фазе.
- Приложения проекта (разные `apps[].path`) одной фичи — разные фазы (не смешивай задачи разных
  приложений, например backend и frontend, в одной фазе).
- **Режь задачи по законченным возможностям, а не по механическим шагам.** Цепочка
  «создать интерфейс» → «создать реализацию» → «подключить» — не декомпозиция: каждая такая задача
  оставляет неиспользуемую границу или неподключённый код, и следующий PR переписывает предыдущий.
  Правильно: «добавить возможность X через существующую границу, с первой реализацией и тестами»,
  затем «добавить политику Y, не меняя потребителей».
- Если PRD называет точку вариативности, задача, которая её вводит, сразу ставит границу вместе с
  первой реализацией — так, чтобы следующие задачи расширяли поведение без правок потребителей.
- Не создавай задач-заготовок под абстракцию, которая не нужна ни текущей, ни следующей задаче.
- **Тесты для изменённого кода — часть той же задачи, что меняет код, не отдельная задача
  "написать тесты" в конце фазы.** Если проект проверяет покрытие изменений (patch-coverage) как
  обязательный статус-чек при мёрдже каждого отдельного PR, то PR, добавляющий непокрытый тестами
  код, физически не может быть смёрджен сам по себе, пока отдельный PR с тестами для него не
  подъедет следом. При автономном выполнении (например, Ralph
  loop, где каждая задача = отдельный PR) это превращает весь стек задач фазы в
  немёрджибельный, пока не доедет последняя. Разбивай задачи так, чтобы каждая, меняющая
  исходный код приложения, включала тесты для этого изменения в себя же; отдельная
  "тестовая" задача допустима только для сквозного/интеграционного покрытия, которое не может
  физически появиться раньше, чем весь код фазы уже существует (например, e2e-сценарий поверх
  нескольких фаз).

## Самопроверка перед сохранением файла

Перед тем как записать файл плана — перечитай черновик и сверь с PRD:

- Каждая фаза закрывает конкретный пункт `## Критерии готовности` PRD — перепроверь, что ссылка
  верная (открой PRD и найди пункт дословно, не по памяти).
- Все AC из PRD в сумме покрыты какой-то фазой — ни один не потерян и не задвоен без причины.
- Любая ссылка на ADR/раздел файла правил/номер строки в другом файле — открыта и подтверждена, не
  оценена на глаз.

## Правила

- Читай PRD внимательно — план должен покрывать все пункты `## Критерии готовности` из PRD.
- Не добавляй задачи, которых нет в PRD (ни в `## В скоупе`, ни в `## Предполагаемое дробление на
  подзадачи`, если PRD его содержит) — этот скилл раскладывает PRD на фазы, не придумывает новый
  скоуп.
- Если PRD неполный или в нём остались открытые вопросы (`## Открытые вопросы` не пуст) — задай
  вопрос пользователю перед созданием плана, а не строй план поверх неопределённости.
- Этот скилл не создаёт и не редактирует код, ветки, коммиты или GitHub issues — только сам файл
  плана. Issues заводит отдельный скилл `issues`.
