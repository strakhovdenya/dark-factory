# PRD генератор

Создай PRD (Product Requirements Document) для следующей фичи: $ARGUMENTS

Сохрани результат в файл `PRD-$ARGUMENTS.md` (переведи название фичи на английский и kebab-case,
например `PRD-cover-letter-export.md`) в каталоге `docs.prd` из `.factory/profile.json`. Если поля
`docs.prd` в профиле нет — не выбирай каталог сам, спроси пользователя, куда сохранить PRD. Если
каталога нет — создай его.

Этот PRD — не GitHub Issue. Это документ уровня "что и зачем", который предшествует им: после
согласования PRD с пользователем следующий шаг — скилл `plan` (разбить PRD на фазы), затем скилл
`issues` (завести фазы/задачи как milestones/issues на GitHub — источник правды). Для фичи,
умещающейся в один PR (не эпик — см. "Режим эпика" ниже), задача заводится как один GitHub Issue
напрямую, тем же форматом (раздел "Формат Issue" скилла `issues`), без промежуточного plan-файла.
Не подменяй эти шаги — PRD не должен содержать детальный implementation-план (это задача самого
Issue, per скилл `issues` («Формат Issue»), на этапе Issue-first protocol из скилла
`task-lifecycle`).

## Перед тем как писать

Прочитай (кратко, только нужные секции — не файлы целиком):

- Файлы правил проекта из `ruleFiles` профиля `.factory/profile.json` (архитектура, структура
  репозитория, правила, обязательные для фичи).
- Файл ADR проекта (`docs.adr` профиля), если он настроен — проверь, не противоречит ли фича
  принятому решению и не относится ли она к теме, уже закрытой решением (если противоречит — не
  игнорируй молча, вынеси в `## Открытые вопросы` секцию ниже).
- Документ с правилами скоупа или бэклогом проекта, если он есть, — чтобы не предлагать фичу,
  которая тайно двигает отложенную функциональность в текущий скоуп.
- Открытые issues/milestones на GitHub (`gh issue list`, а также GitHub Project `githubProject`
  профиля, если он задан) — не дублирует ли фича то, что уже в работе или уже сделано.
- **Если фича уже описана как эпик/фаза** — найди её по правилам скилла `epic-discovery`. Прочитай
  **весь** раздел этого эпика целиком (Goal/Business Value/Scope/Out of Scope/Dependencies/
  Acceptance Criteria), а не только Goal — это обязательный источник, а не справочный контекст:
  разделы "В скоупе"/"Не в скоупе"/"Критерии готовности" итогового PRD должны быть построены как
  явная сверка с этим списком пункт за пунктом, а не пересказом по памяти. Не доверяй файлу
  сводки прогресса как источнику статуса (см. тот же скилл).

## Структура документа

```markdown
# PRD: {название фичи}

**Дата**: {текущая дата}
**Статус**: Draft
**Затрагиваемая часть проекта**: {приложение/пакет из `apps` профиля, либо несколько}
**Связанный issue/backlog-пункт**: {ссылка на существующий GitHub issue, если уже есть, либо
"новая фича — ещё не заведена как issue"}

## Цель

Одно-два предложения: что и зачем это нужно пользователю проекта.

## Контекст и согласованность с проектом

- Какой слой/модуль проекта это затрагивает (по файлам правил проекта).
- Какие существующие артефакты, данные или контракты проекта это затрагивает — если да,
  перечисли какие.
- Связанные ADR (номер + одна строка сути), если фича продолжает или пересекается с уже принятым
  решением.

## Зависимости

Что должно уже быть DONE, прежде чем эта фича имеет смысл технически (не просто "было бы неплохо
сделать сначала", а реальная предпосылка). Если фича соответствует эпику из определения эпиков
проекта — скопируй сюда его `## Dependencies` список пункт за пунктом (номер эпика/фазы + текущий
статус: DONE/в работе/не начато), не пересказывай своими словами и не сокращай список. Если какая-то
зависимость ещё не DONE — это не повод молчать, вынеси конфликт в `## Открытые вопросы`. Если
фича не завязана на эпик и явных технических предпосылок нет — напиши "Явных зависимостей не
найдено".

## Пользовательские сценарии

- Пользователь {действие} -> {результат}

## В скоупе

Конкретный список того, что входит в эту итерацию фичи.

## Не в скоупе

Явно то, что не делаем сейчас (со ссылкой на решение, если оно есть). Если фича граничит с
отложенной функциональностью, явно скажи, что эта часть остаётся за скобками. Если фича
соответствует эпику — каждый пункт его `## Out of Scope` должен быть представлен здесь (своими
словами нормально, пропускать пункты — нет).

## Влияние на конечный автомат (если применимо)

Заполняй только если фича меняет состояние, статус или другой enum-переход. Формат — таблица, как
того требуют Key Invariants issue-контракта и скилл `task-lifecycle`:

| Action | Precondition | Field A after | Field B after | Status after |
|---|---|---|---|---|

Если не применимо — напиши "Не применимо: фича не меняет состояние."

## Влияние на модель данных

Новые/изменённые сущности или поля данных, ожидаемая необходимость миграции. Учитывай, где проект
хранит данные и где — крупные артефакты (по файлам правил проекта).

## API-поверхность

Новые/изменённые внешние интерфейсы (HTTP endpoints, CLI, события). Если правила проекта требуют
описания интерфейсов (например, аннотаций для документации API) — упомяни это как требование, не
как факт (реализация будет в самой задаче, не в PRD).

## Ключевые инварианты

Неочевидные правила, которые ограничивают реализацию этой фичи. Проверяй в первую очередь правила
из файлов правил проекта и принятые ADR, которые касаются затрагиваемой части.

- **Точка вариативности** (обязательный пункт) — какая часть фичи будет меняться независимо
  (провайдер, политика/правило, формат/рендерер, хранилище, шаг пайплайна) и через какую
  существующую границу она меняется. Если текущей границы хватает — так и напиши; если
  вариативной части нет — напиши "Точки вариативности нет". Не предлагай новую абстракцию «на
  будущее»: она оправдана только второй реализацией сейчас или уже запланированной.

## Технические ограничения

Известные ограничения, которые нужно учесть (например: не привязываться к конкретному внешнему
SDK; unit-тесты не должны зависеть от внешних сервисов — по правилам проекта).

Если фича вводит новую изменяемую политику, её последующая замена не должна требовать правок
несвязанных модулей оркестрации/домена.

## Критерии готовности (Acceptance Criteria)

Проверяемые, конкретные пункты — этот список должен быть готов к прямому копированию в будущий
GitHub Issue `## Acceptance Criteria`.

- [ ] Критерий 1
- [ ] Критерий 2

Если фича соответствует эпику — каждый пункт его `## Acceptance Criteria` должен быть представлен
здесь. Любой критерий, которого нет в исходном эпике, но который ты добавляешь сам (например, по
прямому требованию правил проекта, не упомянутому явно в эпике) — помечай инлайн-пометкой вроде
`*(добавлено этим PRD, не из определения эпика — обоснование: ...)*`, чтобы при чтении было видно,
что взято из источника, а что добавлено сверху.

## Test Requirement (набросок)

Какие типы тестов понадобятся (unit / интеграционные / ручная проверка по правилам проекта) — не
пиши тест-план в деталях, это решается в самом GitHub Issue.

## Открытые вопросы

Всё, что нужно уточнить у пользователя, прежде чем это можно будет оформить как задачу в backlog:
неясности в скоупе, потенциальные конфликты с существующим ADR, недостающие мокапы/данные.

## Документация, которую потребуется обновить

Если фича архитектурная (новый/удалённый/переименованный модуль, изменённый data flow, новый
внешний интерфейс, изменённый конечный автомат, новое ADR-решение) — перечисли, что потребует
обновления по правилам документации проекта: файлы правил, файл ADR, соответствующие документы.

## Предполагаемое дробление на подзадачи (только если это эпик)

{раздел появляется, только если см. "Режим эпика" ниже — иначе не включай его в файл вообще}

Черновой, кандидатный список тем для будущих задач/issues — не сами задачи, это разбивает скилл
`plan` на фазы, а скилл `issues` заводит как GitHub issues. Каждый пункт — тема одной задачи, не
сама задача:

1. {короткое название темы} — {одно предложение, что она покрывает и какой Acceptance Criteria
   из PRD выше в неё попадает}
2. ...

Если темы естественно зависят друг от друга по порядку (например, схема данных → backend endpoint
→ frontend) — перечисли их в этом порядке; это подсказка для последовательности, не жёсткое
требование.

Если эпик достаточно большой, чтобы потребовать `-base` интеграционную ветку — явно скажи это
здесь одной строкой ("Рекомендуется epic base branch:
`task/ISSUE-<tracking-issue-n>-<epic-short-name>-base`, т.к. ..."), но не создавай ветку и не
выбирай номер — это отдельный ручной шаг.
```

## Режим эпика

Если фича по масштабу — это эпик (несколько логически завершённых кусков работы, которые не
имеет смысла закрывать одним PR — например, затрагивает несколько приложений проекта, или состоит
из нескольких независимо тестируемых шагов), включи в документ секцию "## Предполагаемое дробление
на подзадачи" из шаблона выше. Если фича умещается в один PR — не включай эту секцию вообще
(не оставляй пустой заголовок).

Не уверен, эпик это или нет — спроси пользователя явно, а не угадывай.

Этот черновой список — материал для скилла `plan` (разбивка на фазы), а не готовые GitHub issues.
Финальные issues (с точным `## Затрагивает`, `## Acceptance Criteria` в формате скилла `issues`)
заводятся тем скиллом из плана; этот скилл их не создаёт.

## Самопроверка перед сохранением файла

Перед тем как записать PRD-файл, перечитай собственный черновик и сверь его с источниками —
не полагайся на память о том, что ты только что прочитал:

- **Каждое утверждение о механике проекта** (инварианты, поведение сервиса, поведение миграций/
  seed-скриптов и т.п.) — перепроверь дословно по файлу-источнику, а не по пересказу. Формулировки
  инвариантов в файлах правил пишутся точно намеренно, и перефразирование легко превращает их в
  противоположное по смыслу утверждение.
- **Каждая ссылка на диапазон строк** в документе проекта — открой файл и подтверди диапазон, не
  оценивай на глаз.
- **Если фича соответствует эпику** — построчно сверь итоговые `## В скоупе`, `## Не в скоупе`,
  `## Зависимости`, `## Критерии готовности` с оригинальными списками эпика: каждый пункт источника
  представлен, и любой пункт, добавленный сверх источника, явно помечен (см. правило выше).
- **Точка вариативности** в `## Ключевые инварианты` либо названа вместе с границей, через которую
  меняется, либо явно отмечено, что её нет; пустого или размытого пункта («код должен быть гибким»)
  нет.
- Если в процессе самопроверки нашлась неточность — исправь её до сохранения файла, не сохраняй
  черновик с известной ошибкой в расчёте на последующую правку.

## Правила

- Пиши конкретно — никакой воды.
- Критерии готовности должны быть проверяемыми (checkbox-формат, без расплывчатых формулировок
  типа "работает хорошо").
- Не описывай, КАК реализовывать (код, конкретные файлы, шаги) — только ЧТО и ЗАЧЕМ. HOW —
  предмет самого GitHub Issue, который пишется отдельно на этапе Issue-first protocol, уже на
  ветке задачи.
- Если описание фичи короткое или неоднозначное — задавай уточняющие вопросы до полного понимания,
  прежде чем создавать файл. В частности уточни: какие приложения проекта затронуты, входит ли
  фича в текущий скоуп или это отложенная функциональность, есть ли готовый мокап/референс.
- Явно проверяй фичу на конфликт с уже принятыми ADR (файл `docs.adr`, если он настроен) и с
  правилами скоупа проекта. Если конфликт есть — не замалчивай и не переписывай решение сам,
  вынеси это в `## Открытые вопросы` и прямо спроси пользователя.
- Не переноси отложенную функциональность в текущий скоуп без явного запроса пользователя.
- Этот скилл не создаёт и не редактирует код, ветки, коммиты — только сам PRD-файл.
